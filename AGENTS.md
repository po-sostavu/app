- Все схемы и диаграммы проекта оформлять в Mermaid в блоках кода mermaid внутри Markdown. Хранить исходник рядом с описанием, обновлять вместе с изменением и проверять синтаксис и отображение. ASCII-схемами и картинками исходник не заменять
GitFlow
- Регламент команды — docs/git-flow.md. Конфигурации и релизы — docs/configuration-and-releases.md
- CD выкладывает проверенный коммит `main` по blue-green: два комплекта PWA и API с общей БД. Порядок переключения, совместимость миграций и откат — docs/configuration-and-releases.md. Production-конфигурация находится в infra/production. Переключатели публикации и выкладки, подтверждение Environment production и режим тестовых данных описаны в docs/cd.md. Локальный infra/compose.yaml запускает один комплект
- Ветки:
  - main — релизы
  - develop — разработка
  - feature/prd-<номер>-<имя> — от develop, PR в develop
  - release/<версия> — от develop, PR в main. Изменения вернуть в develop через PR
- Коммиты:
  - Формат: <type>(<scope>): <описание> (PRD-<номер>)
  - Типы: feat, fix, docs, chore, ci, build, refactor, test
  - Перед коммитом проверить ветку, статус и staged diff
  - Не включать чужие изменения и секреты
  - Разрешение на реализацию не означает разрешение на commit, push или merge. Для этих действий нужно соответствующее поручение пользователя
- PR:
  - Указать задачу Linear, изменения и результаты проверок
  - Ревью и слияние выполнять по действующим правилам доступа GitHub и регламенту команды
  - Пока CI/CD не подключён, фиксировать применимые локальные и ручные проверки в PR. После подключения требовать успешные применимые проверки CI
- Запрещены:
  - Рабочие коммиты и прямые push в main и develop
  - Force push и перезапись общей истории
OpenSpec
- Один экземпляр в корне:
  - config.yaml — контекст и общие правила
  - specs/ — принятое поведение
  - changes/<имя>/:
    - proposal.md
    - design.md
    - tasks.md
    - specs/ — предлагаемые изменения требований
- Изменения связывать с задачами Linear
- Соблюдать этап:
  - Propose — изучить код и требования, зафиксировать неизвестное, подготовить документы без изменения приложения
  - Apply — после согласования плана. Уже полученное согласование повторно не запрашивать
    - Выполнять задачи и отмечать их по фактическим изменениям и результатам проверок
  - Archive — после проверки реализации и строгой валидации. При архивации перенести изменения требований в основные specs/
    - Проверка: openspec validate --all --strict
- Постоянные архитектурные правила хранить в docs/architecture.md и локальных AGENTS.md. Обновлять вместе с реализацией
- В design.md описывать решения конкретного изменения и причины выбора
Надёжность и конкурентность
- При изменении общего состояния учитывать параллельные запросы, гонки данных, потерю обновлений, повторные операции, блокировки и тупики (deadlocks)
- Учитывать несколько экземпляров API: память процесса, локальные mutex и локальный кэш не являются общей координацией между экземплярами
- Для повторяемых команд с побочными эффектами предусматривать ключи идемпотентности. Один ключ соответствует одной логической операции. Повтор с ним не должен дублировать бизнес-изменение или внешний эффект. Детали протокола — в docs/architecture.md и локальных AGENTS.md
- Оценивать отказы и медленные ответы зависимостей. Ограничивать ожидание и повторы, возвращать понятные ошибки. Отказ одного сценария не должен останавливать независимые сценарии
- Защиту и проверки выбирать по конкретному бизнес-риску. Не добавлять блокировки, инфраструктуру и тесты на каждый технический элемент без необходимости
- Подробные архитектурные правила — docs/architecture.md, правила Go — apps/api/AGENTS.md, правила обработки ошибок в интерфейсе — apps/pwa/AGENTS.md
Безопасность
- Секреты внешних сервисов, пароли БД, приватные ключи и ключи подписи хранятся только на серверной стороне. Не помещать их в PWA, VITE_*, исходники, сборки, браузерные хранилища и клиентские ответы
- Секреты получать из защищённой конфигурации окружения или хранилища секретов. Не добавлять их в Git, Docker-образы, примеры конфигурации, логи и отчёты. В .env.example использовать только безопасные заглушки
- Не доверять данным клиента и ответам внешних сервисов или ИИ. Проверять входные данные и доступ к конкретному объекту на сервере. Запрет доступа — по умолчанию
- Использовать параметризованный SQL, защищённые соединения, минимальные права доступа и ограничения ресурсов. Не отключать проверку TLS и другие защитные механизмы ради обхода ошибки
- Не выводить секреты при диагностике. Если обнаружена утечка, сообщить об этом без воспроизведения значения. Удаление строки из файла не заменяет отзыв или ротацию секрета. Перезапись общей Git-истории без поручения запрещена
- Проверки безопасности должны соответствовать реальному риску и затронутым бизнес-правилам. Не создавать тесты на каждый технический элемент
Ответы
- Эти правила действуют для ответов и текстов проекта, если пользователь явно не попросил другой стиль
- Писать естественно, кратко и по делу, как разработчик для коллеги
- Начинать с сути. Не добавлять шаблонные вступления, комментарии о собственном ответе и заключения, повторяющие сказанное
- Использовать простые слова и конкретные действия. Убирать канцелярит, безличные обороты, воду и показной энтузиазм
- Каждое предложение должно добавлять полезную информацию. Не повторять мысль другими словами
- Выбирать тон и подробность под задачу. Не превращать короткий ответ в инструкцию без запроса
- Добавлять заголовки, списки и таблицы, только когда они помогают читать и сравнивать
- В конце пунктов нумерованных и ненумерованных списков не ставить точку или точку с запятой
- В тексте не использовать точку с запятой. Вместо неё начинать новое предложение
- При редактировании сохранять смысл, термины, ограничения, числа, ссылки и исполняемые примеры
- Перед отправкой перечитывать текст и убирать неестественные формулировки, повторы и лишние пояснения
- Сообщать результат, проверки и оставшиеся проблемы
- Не заявлять выполнение действий без подтверждения
