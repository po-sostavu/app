# Регламент работы с конфигурациями и релизами

Документ дополняет [Git Flow](git-flow.md) и [архитектуру](architecture.md). CI/CD и автоматический деплой пока не настроены. Ниже описан порядок действий команды; наличие инструкции не означает, что приложение или тестовый сервер уже готовы.

## 1. Конфигурации

| Окружение | Назначение | Где хранятся значения |
| --- | --- | --- |
| Локальное | Разработка на компьютере участника | Локальные `.env`, исключённые из Git |
| Тестовое | Совместная проверка версии после подготовки сервера | Защищённая конфигурация тестового сервера |
| Рабочее | Выпущенная версия после подготовки окружения | Защищённая конфигурация рабочего сервера |

Окружения используют отдельные БД, учётные данные и ключи. Разработчик не копирует рабочие секреты или пользовательские данные в тестовое окружение.

В Git хранятся исходники, несекретные настройки инструментов, безопасные `.env.example` и файлы зависимостей. По мере реализации приложений фиксируются `pnpm-lock.yaml`, `go.mod`, `go.sum`, версии инструментов и базовых образов. Зависимости и конфигурация меняются через PR вместе с затронутым кодом.

Пути примеров соответствуют архитектуре: `infra/.env.example` — для совместного запуска, примеры конкретных приложений — рядом с ними по мере появления конфигурации. Пока параметры не реализованы, вымышленные рабочие `.env.example` не создаются.

При добавлении или изменении параметра автор:

1. Добавляет имя и безопасный пример в соответствующий `.env.example`.
2. Описывает назначение, обязательность, формат, значение по умолчанию, секретность и окружения, в которых он нужен.
3. Указывает необходимость пересборки, перезапуска или миграции; проверяет совместимость со старой конфигурацией и обновляет инструкцию запуска.
4. Проверяет загрузку корректной конфигурации и понятную ошибку при отсутствии обязательных значений. В PR приводит результат без раскрытия секретов.

Сервер получает секреты из окружения или хранилища секретов. Пароли БД, ключи ИИ-сервиса и ключи подписи не помещаются в PWA, `VITE_*`, Git, Docker-образы, логи и отчёты. Параметры `VITE_*` следует считать публичными: они попадают в клиентскую сборку.

`.gitignore` исключает `.env` и `.env.*`, сохраняя безопасные `.env.example` и `.env.<окружение>.example`. Исключение не удаляет уже отслеживаемый файл из истории. При утечке владелец ключа отзывает или заменяет его, затем исправляется источник утечки; удаления строки недостаточно.

## 2. Версии и ответственность

Формат версии — `MAJOR.MINOR.PATCH`: несовместимые изменения, совместимые новые возможности, исправления. До стабильной версии используется серия `0.x.y`, а совместимость явно описывается в каждом выпуске. Ветка — `release/0.1.0`, тег — `v0.1.0`; кандидат при необходимости — `v0.1.0-rc.1`.

В монорепозитории выпуск фиксирует совместимый набор PWA, API и конфигурации одним тегом. Опубликованный тег не перемещается и не переиспользуется; исправление получает новую версию.

Автор отвечает за код, конфигурацию и проверки. Ревьюер проверяет PR по регламенту. Ответственный за релиз принимает выпуск и сливает PR в `main` согласно действующим правам доступа. Ответственный за окружение перед выкладкой проверяет секреты, резервную копию и возможность отката; его имя фиксируется в описании выпуска.

## 3. Подготовка и выпуск

1. Выбрать состав и номер версии. Убедиться, что нужные задачи слиты в `develop`, а доступные проверки прошли. Создать `release/<версия>` от выбранного коммита `develop` и отправить её в GitHub.

   ```sh
   git fetch origin
   git switch develop
   git pull --ff-only origin develop
   git switch -c release/0.1.0
   git push -u origin release/0.1.0
   ```

   Пример выполняется при чистом дереве; существующую ветку не создавать повторно. Создание ветки ещё не означает выпуск. Если она создана до готовности приложения, сначала перенести готовый состав через PR `develop → release/0.1.0`, проверить его и только затем объявить заморозку состава.

2. После заморозки добавлять только исправления через PR из отдельных веток, созданных от этой release-ветки. Новые возможности продолжают разрабатываться в `develop`.
3. Подготовить описание выпуска: версия, изменения и задачи, commit SHA, результаты проверок, параметры, миграции, известные ограничения, ответственный и порядок отката. Пока приложения нет, выпуск не объявлять готовым.
4. Когда тестовое окружение будет готово, вручную развернуть конкретный коммит кандидата по актуальной инструкции запуска. Проверить затронутые сценарии и совместимость PWA, API и БД. Зафиксировать окружение, дату и результат. Сейчас сервер и автоматический деплой в рамках этой настройки не создаются.
5. Открыть PR `release/<версия> → main`. После проверок и соблюдения правил доступа ответственный выполняет **Create a merge commit**.
6. Получить слитую `main`, поставить аннотированный тег на проверенный коммит релиза и опубликовать его. Для примера `0.1.0`:

   ```sh
   git fetch origin
   git switch main
   git pull --ff-only origin main
   git log -1 --oneline
   git tag -a v0.1.0 -m "Release 0.1.0"
   git push origin v0.1.0
   ```

   До создания тега сверить SHA с принятым PR: если `main` уже продвинулась, указать нужный SHA явно. Одноимённый тег не перезаписывать. Оформить GitHub Release с этим тегом и описанием из шага 3.
7. Открыть PR `main → develop` и слить через **Create a merge commit**, чтобы вернуть релизные исправления. При конфликте создать рабочую feature-ветку от актуальной `develop`, влить `origin/main`, разрешить конфликт и направить её PR в `develop`. Убедиться, что релизный коммит входит в историю `develop`.

Ветки `main`, `develop` и `release/*` защищены от удаления и остаются в репозитории. Для следующего выпуска создаётся новая release-ветка. Завершённые feature-ветки можно удалить после слияния.

## 4. Откат и исправления

Перед выкладкой фиксируются предыдущая рабочая версия и совместимая конфигурация. При миграции БД заранее проверяются резервная копия и способ восстановления. Миграции версионируются; уже применённую миграцию не переписывают, исправление оформляют новой.

Если после выкладки нарушен основной сценарий, ответственный останавливает продвижение версии и возвращает предыдущую проверенную сборку с совместимой конфигурацией. Откат приложения допустим только при совместимости с текущей схемой БД. Иначе используется заранее проверенный план миграции или восстановления с оценкой возможной потери данных; произвольный откат БД не выполняется.

В задаче и описании выпуска фиксируются причина, затронутая версия, действия и результат повторной проверки. Git-история и старые теги сохраняются. Исправление проводится через новую feature-ветку, проверки и следующий выпуск. Для срочного исправления выпущенной версии при необходимости создаётся новая patch release-ветка от последнего стабильного тега. Это исключение из обычной базы `develop` явно отмечается в релизном PR; исправления затем возвращаются в `develop` тем же порядком.

Регламент не вводит автоматических тестов, сборки или развёртывания. Они будут подключены отдельной задачей CI/CD.
