# Регламент работы с конфигурациями и релизами

Правила дополняют [устав](charter.md), [Git Flow](git-flow.md) и [архитектуру](architecture.md). [CI](ci.md) проверяет и собирает приложения. [CD](cd.md) выкладывает выпуск из `main` после успешного CI этого коммита и подтверждения Environment production, по схеме blue-green из раздела 5. Изменения в `develop` и PR сами по себе не запускают выкладку. Тег фиксирует выпуск, отдельный повторный деплой по тегу не требуется.

## 1. Конфигурации

| Окружение | Назначение | Где хранятся значения |
| --- | --- | --- |
| Локальное | Разработка на компьютере участника | Локальные `.env`, исключённые из Git |
| Тестовое | Совместная проверка версии после подготовки сервера | Защищённая конфигурация тестового сервера |
| Рабочее | Выпущенная версия после подготовки окружения | Защищённая конфигурация рабочего сервера |

Окружения используют отдельные БД, учётные данные и ключи. Разработчик не копирует рабочие секреты или пользовательские данные в тестовое окружение.

CI выполняется без серверных секретов и env-файлов: PWA собирается с публичным адресом `/api`, API проверяется существующими тестами. Docker-образы сохраняются в Artifacts и проверяются на изолированном стенде. CD публикует эти образы без пересборки, а серверный обработчик запускает мигратор и новый комплект приложения.

В Git хранятся исходники, несекретные настройки инструментов, безопасные `.env.example` и файлы зависимостей. По мере реализации приложений фиксируются `package-lock.json`, `go.mod`, `go.sum`, версии инструментов и базовых образов. Зависимости и конфигурация меняются через PR вместе с затронутым кодом.

`infra/.env.example` содержит параметры совместного запуска. Примеры приложений хранятся рядом с ними. В `.env.example` добавляются только реализованные параметры.

При реализации лимитов бесплатный месячный объём задаётся серверной конфигурацией. Исходный ориентир устава — 10 сканирований. Размер демопакета, смена месяца, срок действия, ограничения активации и влияние изменения настроек на существующие остатки определяются до разработки счётчика. Расчётные 20 сканирований за 199 ₽ из устава не являются утверждённым тарифом. В MVP доступна только явно обозначенная демоактивация без платёжных данных. Включение реальных оплат или подписки конфигурационным флагом не считается согласованным расширением продукта.

При добавлении или изменении параметра автор:

1. Добавляет имя и безопасный пример в соответствующий `.env.example`
2. Описывает назначение, обязательность, формат, значение по умолчанию, секретность и окружения, в которых он нужен
3. Указывает необходимость пересборки, перезапуска или миграции. Проверяет совместимость со старой конфигурацией и обновляет инструкцию запуска
4. Проверяет загрузку корректной конфигурации и понятную ошибку при отсутствии обязательных значений. В PR приводит результат без раскрытия секретов

Сервер получает секреты из окружения или хранилища секретов. Пароли БД, ключи OCR- и ИИ-сервисов и ключи подписи не помещаются в PWA, `VITE_*`, Git, Docker-образы, логи и отчёты. Параметры `VITE_*` публичны: они попадают в клиентскую сборку.

`.gitignore` исключает `.env` и `.env.*`, сохраняя безопасные `.env.example` и `.env.<окружение>.example`. Исключение не удаляет уже отслеживаемый файл из истории. При утечке владелец ключа отзывает или заменяет его, затем исправляется источник утечки. Удаления строки недостаточно.

## 2. Версии и ответственность

Формат версии — `MAJOR.MINOR.PATCH`: несовместимые изменения, совместимые новые возможности, исправления. До стабильной версии используется серия `0.x.y`, а совместимость явно описывается в каждом выпуске. Ветка — `release/0.1.0`, тег — `v0.1.0`. Кандидат при необходимости — `v0.1.0-rc.1`.

В монорепозитории выпуск фиксирует совместимый набор PWA, API и конфигурации одним тегом. Опубликованный тег не перемещается и не переиспользуется. Исправление получает новую версию.

Версия выпуска не заменяет версию HTTP API. Для каждого выпуска перечисляются поддерживаемые основные версии API и сборки PWA, включая ранее установленные. Правила `/api/v1`, совместимых изменений и прекращения поддержки — в [архитектуре](architecture.md#версии-api-и-совместимость-с-pwa). Серия `0.x.y` не разрешает ломать уже опубликованный клиент.

Автор отвечает за код, конфигурацию и проверки. Ревьюер проверяет PR по регламенту. Ответственный за релиз принимает выпуск и сливает PR в `main` согласно действующим правам доступа. Ответственный за окружение перед выкладкой проверяет секреты, резервную копию и возможность отката. Его имя фиксируется в описании выпуска.

## 3. Подготовка и выпуск

1. Выбрать состав и номер версии. Убедиться, что нужные задачи слиты в `develop`, а доступные проверки прошли. Создать `release/<версия>` от выбранного коммита `develop` и отправить её в GitHub

   ```sh
   git fetch origin
   git switch develop
   git pull --ff-only origin develop
   git switch -c release/0.1.0
   git push -u origin release/0.1.0
   ```

   Пример выполняется при чистом дереве. Существующую ветку не создавать повторно. Если ветка создана до готовности приложения, сначала перенести готовый состав через PR `develop → release/0.1.0`, проверить его и только затем объявить заморозку состава

2. После заморозки добавлять только исправления через PR из отдельных веток, созданных от этой release-ветки. Новые возможности продолжают разрабатываться в `develop`
3. Подготовить описание выпуска: версия, изменения и задачи, commit SHA, результаты проверок, параметры, миграции, известные ограничения, ответственный и порядок отката. Указать поддерживаемые сборки PWA и версии API, результаты проверки старых клиентов с новым сервером и новой PWA с сервером для отката. Пока приложения нет, выпуск не объявлять готовым
4. Проверить кандидата на изолированном стенде: затронутые сценарии и совместимость PWA, API и БД. Зафиксировать окружение, дату и результат. CI запускает проверку двух цветов с готовыми образами. Общий VPS получает выпуск только после попадания в `main`, успешного CI и подтверждения Environment production
5. Открыть PR `release/<версия> → main`. После проверок и соблюдения правил доступа ответственный выполняет **Create a merge commit**
6. Получить слитую `main`, поставить аннотированный тег на проверенный коммит релиза и опубликовать его. Для примера `0.1.0`:

   ```sh
   git fetch origin
   git switch main
   git pull --ff-only origin main
   git log -1 --oneline
   git tag -a v0.1.0 -m "Release 0.1.0"
   git push origin v0.1.0
   ```

   После слияния дождаться CI и публикации образов в CD. Проверить состав выпуска, подтвердить Environment production и дождаться выкладки. Проверить HTTPS, readiness и SHA выпуска. До создания тега сверить SHA с принятым PR: если `main` уже продвинулась, указать нужный SHA явно. Одноимённый тег не перезаписывать. Оформить GitHub Release с этим тегом и описанием из шага 3
7. Открыть PR `main → develop` и слить через **Create a merge commit**, чтобы вернуть релизные исправления. При конфликте создать рабочую feature-ветку от актуальной `develop`, влить `origin/main`, разрешить конфликт и направить её PR в `develop`. Убедиться, что релизный коммит входит в историю `develop`

Ветки `main`, `develop` и `release/*` защищены от удаления и остаются в репозитории. Для следующего выпуска создаётся новая release-ветка. Завершённые feature-ветки можно удалить после слияния.

## 4. Откат и исправления

Перед выкладкой фиксируются предыдущая рабочая версия и совместимая конфигурация. При миграции БД заранее проверяются резервная копия и способ восстановления. Миграции версионируются. Уже применённую миграцию не переписывают, исправление оформляют новой.

Первый тестовый стенд каркаса использует явный `mode: test` по [регламенту CD](cd.md). Для заменяемых тестовых данных внешние копии и пробное восстановление отложены владельцем. Локальная копия перед миграцией обязательна. Перед рабочими данными стенд переводится в production с проверенным восстановлением.

Если после выкладки нарушен основной сценарий, ответственный останавливает продвижение версии и возвращает предыдущую проверенную сборку с совместимой конфигурацией. Откат приложения допустим только при совместимости с текущей схемой и данными БД, а также с PWA, уже полученными пользователями. Откат сервера не откатывает установленную PWA. Если совместимости нет, простое переключение назад запрещено: применяется заранее проверенный план исправления или восстановления с оценкой возможной потери данных. Произвольный откат БД не выполняется.

В задаче и описании выпуска фиксируются причина, затронутая версия, действия и результат повторной проверки. Git-история и старые теги сохраняются. Исправление проводится через новую feature-ветку, проверки и следующий выпуск. Для срочного исправления выпущенной версии при необходимости создаётся новая patch release-ветка от последнего стабильного тега. Это исключение из обычной базы `develop` явно отмечается в релизном PR. Исправления затем возвращаются в `develop` тем же порядком.

Автоматические проверки и сборка описаны в [регламенте CI](ci.md). Готовность релиза и тестового окружения проверяется отдельно от CI. Порядок подтверждения выкладки и ограничения тестового режима описаны в [регламенте CD](cd.md).

## 5. Blue-green развёртывание

Blue и green — два независимо запускаемых комплекта PWA с Caddy и Go API. Один принимает пользовательский трафик, во втором проверяется следующий выпуск. У каждого комплекта своя сеть приложения, чтобы его Caddy обращался к API той же версии. На обследованном VPS внешний Traefik должен направлять домен в активный Caddy. Маршрут и сертификаты ещё предстоит настроить.

PostgreSQL, её данные и резервные копии общие для обоих комплектов и управляются отдельно от их жизненного цикла. Переключение цвета не создаёт, не копирует и не откатывает БД. Сессии, идемпотентность и другое общее состояние должны работать между обоими выпусками. Старый и новый API не запускают миграции при старте. Общая БД относится только к двум цветам одного окружения, тестовое и рабочее окружения по-прежнему разделены.

Порядок CD, реализованный в [конфигурации и серверном обработчике](cd.md):

1. После успешного CI коммита `main` опубликовать проверенные образы и зафиксировать их digest, commit SHA и конфигурацию выпуска. На VPS загружать именно эти образы. Плавающий `latest` не определяет версию выкладки
2. Заблокировать параллельную выкладку в это окружение. Идущий деплой не обрывать новым push в середине миграции или переключения. Зафиксировать активный цвет, предыдущие образы, конфигурацию и проверенный план отката
3. Проверить резервную копию и ресурсы для одновременной работы двух комплектов, общей БД и существующих сервисов VPS. Учесть суммарные пулы соединений, CPU, RAM и диск. При нехватке ресурсов остановить выкладку до изменений, сохранив активный комплект
4. Выполнить миграции один раз отдельной задачей. На этом этапе допустимы только изменения, совместимые с работающей и новой версиями API. Ошибка миграции блокирует дальнейшую выкладку, dirty-состояние автоматически не снимается
5. Запустить неактивный комплект без публичного переключения. Проверить PWA, readiness API, нужную схему БД и затронутые сценарии через его Caddy. Проверить поддерживаемые старые PWA с новым API и новую PWA с сервером для отката. Один `/readyz`, проверяющий соединение с БД, не подтверждает готовность продукта
6. Переключить маршрут домена на подготовленный комплект и проверить результат через публичный адрес. Новые запросы должны идти в новый комплект, уже начатым запросам старого дать ограниченное время на завершение. Прокси не повторяет команды с побочными эффектами вслепую
7. Наблюдать ошибки и задержки в течение окна, указанного в описании выпуска. До его окончания сохранить старый комплект для быстрого возврата трафика. Откат допустим только при выполнении условий раздела 4, после него снова проверить публичный адрес
8. После завершения окна отката остановить старый комплект. Сохранить необходимые образы, конфигурацию и файлы поддерживаемых PWA. Удаление старого цвета не удаляет общую БД или файлы, ещё нужные клиентам. В журнале выкладки зафиксировать SHA, digest, активный цвет и результаты проверок

Схема БД меняется поэтапно: сначала добавить совместимые поля и структуры, затем перевести код и данные, и только отдельным последующим выпуском удалить устаревшее. Удаление допускается после прекращения использования всеми поддерживаемыми версиями API и завершения окна отката. Наличие `.down.sql` не доказывает безопасность отката с уже записанными новыми данными.

Развёртывание на одном VPS требует ресурсов на два комплекта приложения и не защищает от отказа самого сервера или общей БД. `infra/compose.yaml` поднимает один локальный комплект. VPS использует отдельные Compose в `infra/production` и установленный серверный обработчик. [Первый тестовый выпуск](releases/0.1.0.md) прошёл проверку ресурсов и HTTPS. Перед каждым следующим выпуском проверяются совместимость и доступный запас. Перед рабочими данными обязательны внешние копии и проверенное восстановление. Находки в Caddy и gosu устранены. Результаты и оставшиеся ограничения описаны в [проверке контейнеров](container-security.md).
