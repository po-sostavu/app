# Регламент Git Flow и code review

Регламент действует для [po-sostavu/app](https://github.com/po-sostavu/app). Задачи ведутся в Linear. CI/CD пока не подключён: автор выполняет применимые проверки локально и записывает результат в PR.

## 1. Ветки

| Ветка | Назначение | Откуда создаётся | Куда направляется PR |
| --- | --- | --- | --- |
| `main` | История принятых релизов | Постоянная ветка | После релиза — в `develop`, чтобы вернуть изменения |
| `develop` | Общая ветка разработки | Постоянная ветка | Готовый срез переносится в `release/*` |
| `feature/prd-<номер>-<имя>` | Одна задача Linear | Актуальная `develop` | `develop` |
| `release/<версия>` | Подготовка конкретной версии | Проверенный коммит `develop` | `main` |

`feature/*` и `release/*` — шаблоны имён. Ветки с буквальным символом `*` не создаются. Имя задачи пишется латиницей через дефисы: `feature/prd-30-git-flow`. Имя релизной ветки содержит версию: `release/0.1.0`.

В релизной ветке исправляются только ошибки и документы выпуска. Для исправления создаётся отдельная `feature/prd-<номер>-<имя>` от соответствующей `release/<версия>`, а PR направляется в неё. Это исключение из обычной базы `develop` указывается в PR.

## 2. Работа над задачей

Перед началом проверить рабочее дерево. Незакоммиченные изменения другой задачи сначала сохранить отдельно; команды ниже выполняются при чистом дереве.

```sh
git status --short --branch
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/prd-30-git-flow
```

Имя в примере заменить именем своей задачи. Если ветка существует, перейти в неё через `git switch`, не создавать повторно.

1. Выполнить задачу и обновить связанные документы. Для изменений поведения продукта соблюдать порядок OpenSpec из корневого `AGENTS.md`.
2. Запустить доступные проверки затронутой части проекта. Команды брать из текущей документации приложения; целевые команды из архитектуры не считать уже реализованными.
3. Просмотреть изменения, добавить только нужные файлы и проверить staged diff.
4. Создать коммит, отправить feature-ветку и открыть PR в `develop` по шаблону репозитория.

```sh
git diff --check
git diff
git add docs/git-flow.md
git diff --cached
git commit -m "docs(git): описать регламент команды (PRD-30)"
git push -u origin feature/prd-30-git-flow
```

Пути, ветка и текст коммита — примеры для конкретной задачи. Формат коммита: `<type>(<scope>): <описание> (PRD-<номер>)`. Типы: `feat`, `fix`, `docs`, `chore`, `ci`, `build`, `refactor`, `test`.

Если целевая ветка изменилась, влить её актуальное состояние в рабочую ветку обычным merge, разрешить конфликты, повторить проверки и отправить новый коммит. Для обычной feature-ветки:

```sh
git fetch origin
git merge origin/develop
```

Для исправления релиза вместо `origin/develop` использовать соответствующую `origin/release/<версия>`. Общую историю не переписывать; force push запрещён.

## 3. PR, ревью и слияние

Автор указывает ссылку на задачу, суть изменения, команды или шаги проверки и их результаты. Изменения конфигурации, миграции и ограничения описываются отдельно. Чужие изменения и секреты не включаются.

Ревьюер — другой участник с правом записи. Он проверяет:

- Соответствие задаче и правильность целевой ветки.
- Корректность поведения, обработку ошибок и существенные пограничные случаи.
- Понятность изменений, соблюдение архитектуры и отсутствие секретов.
- Достаточность проверок, совместимость конфигурации и документации.

Замечание содержит место, проблему и ожидаемое исправление. При блокирующей проблеме ревьюер выбирает **Request changes**, после исправления — **Approve**. Ответы остаются в PR. Новые изменения требуют повторной проверки; GitHub сбрасывает устаревшее одобрение для участников, которым оно обязательно.

Ревью и слияние выполняются по действующим правилам доступа GitHub. Применимые проверки и описание изменения нужны в любом случае. За принятие релиза в `main` отвечает ответственный за релиз; в `develop` и `release/*` PR сливает участник с соответствующим правом.

Команда использует **Create a merge commit**, особенно при `release/* → main → develop`, чтобы сохранять общий граф. Squash и rebase технически доступны в GitHub, но не используются для этих переходов. После слияния feature-ветку можно удалить; `main`, `develop` и `release/*` сохраняются под защитой от удаления.

## 4. Защита веток в GitHub

Правила задаются в [Settings → Rules → Rulesets](https://github.com/po-sostavu/app/settings/rules), с режимом **Active**. Файл регламента сам по себе защиту не включает.

| Правило | `main` | `develop`, `release/*` |
| --- | --- | --- |
| Изменения только через PR | Включено | Включено |
| Удаление и force push | Запрещены всем | Запрещены всем |
| Кто может сливать | По настроенным правам доступа | По настроенным правам доступа |
| Правило ревью | Одно одобрение | Одно одобрение |
| Сброс одобрения после новых изменений | Включён в правиле ревью | Включён в правиле ревью |
| Закрытие обсуждений | Включено в базовом правиле и правиле ревью | Включено в правиле ревью |
| Обязательные статусы CI | Пока не настроены | Пока не настроены |

Защита PR и истории хранится отдельно от требования ревью. При изменении шаблонов веток сохраняются существующие права доступа. Настройка правил не должна разрешать прямой push, force push или удаление защищённых веток.

Проверка: открыть rulesets, проверить `Active`, шаблоны `refs/heads/main`, `refs/heads/develop`, `refs/heads/release/*`, состав правил и права доступа. Участники должны иметь доступ для создания PR и ревью. Справка: [GitHub Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

## 5. Практика code review

1. Каждый участник выбирает небольшое самостоятельное изменение и открывает свой PR из feature-ветки в `develop`.
2. Команда распределяет ревью по кругу: каждый проверяет PR следующего участника, последний — PR первого.
3. Ревьюер изучает diff и результат проверки, оставляет содержательный итог. Ошибки не нужно придумывать; для корректного PR достаточно объяснить, что проверено, и поставить Approve.
4. Автор исправляет найденные проблемы; ревьюер повторно проверяет изменения.
5. После слияния команда собирает ссылки на PR участников и выполненные ими ревью. Ссылка должна вести на конкретный PR или review.

Практика завершена, когда каждый участник создал реальный PR и провёл ревью чужого изменения. Наличие регламента само по себе не подтверждает выполнение.
