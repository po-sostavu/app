# Проверки CI

Конфигурация — [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). Это часть [PRD-31](https://linear.app/po-sostavu/issue/PRD-31): проверки PWA, Go API и контейнерной сборки. CD и тестовый сервер настраиваются отдельно.

## Запуск и результат

Workflow `CI` запускается при открытии, обновлении и повторном открытии PR в `develop` или `main`, а также при push в эти ветки. Проверяются оба приложения, в том числе при изменении документации: фильтров по путям нет. Новый запуск для того же события и PR или ветки отменяет устаревший.

После публикации feature-ветки первый запуск выполняется через PR. Ручной запуск **Actions → CI → Run workflow** становится доступен после появления workflow в default branch репозитория. Само наличие YAML не подтверждает успешный запуск GitHub Actions: в PR нужно указать ссылку на выполненный workflow и проверенный commit SHA.

Итоговый статус `CI status` успешен, только когда успешно завершены PWA, API и все сборки Docker. Ошибка, пропуск или отмена обязательного задания не дают успешного итогового статуса. Причина ошибки находится в логах соответствующего задания; после исправления нужно отправить новый коммит и дождаться его проверок.

## Что проверяется

| Задание           | Проверки                                                                                                 |
| ----------------- | -------------------------------------------------------------------------------------------------------- |
| PWA               | `npm ci`, `npm run check`, `npm run build`; аудит зависимостей                                           |
| API               | `task api:fmt:check`, `task api:lint`, `task api:test:race`, `task api:build`, `task api:audit` из корня |
| Docker (pwa)      | Сборка статики PWA и общего шлюза, target `runtime`                                                      |
| Docker (api)      | Сборка Go API, target `api`                                                                              |
| Docker (migrate)  | Сборка отдельного инструмента миграций, target `migrate`                                                 |
| Docker (postgres) | Сборка локального PostgreSQL с обновлённой zlib, target `runtime`                                        |
| CI status         | Итог результатов всех заданий                                                                            |

`npm run check` включает Prettier, ESLint, Steiger, проверку типов TypeScript и существующие тесты Vitest. Go-тесты запускаются с race detector; отдельный повтор обычного `go test` не нужен. Форматирование в CI только проверяется, файлы автоматически не исправляются.

Сборочный контекст PWA — корень репозитория, Dockerfile — `apps/pwa/Dockerfile`. API и миграции собираются из `apps/api`, цели — `api` и `migrate`. PostgreSQL собирается из `infra/postgres`, цель — `runtime`. Матрица включает четыре Docker-сборки. Образы не публикуются, контейнеры не разворачиваются. Успешная сборка не заменяет проверку запуска приложения или аудит содержимого базового образа.

Существующие тесты каркасов не проверяют ещё не реализованные продуктовые сценарии. PostgreSQL и внешние OCR/ИИ API для этих заданий не запускаются. Интеграционные проверки с отдельной PostgreSQL добавляются вместе с бизнес-инвариантами, зависящими от БД.

## Версии и безопасность

Задания выполняются на `ubuntu-24.04`. Node.js берётся из `apps/pwa/.nvmrc`, npm — из `packageManager` в `apps/pwa/package.json`, Go — из `apps/api/go.mod`. Task закреплён на `3.54.0`. Версии линтера и govulncheck берутся из `apps/api/tools/go.mod`. Кэш npm привязан к `package-lock.json`, кэш Go — к `go.sum` приложения и инструментов.

Actions закреплены полными commit SHA с комментариями версий. Токен workflow имеет только `contents: read`, checkout не сохраняет Git credentials. Рабочие секреты, данные пользователей и доступ к серверу не нужны. Используется `pull_request`, выполнение кода PR через `pull_request_target` не предусмотрено. У заданий ограничено время выполнения.

Политика аудита:

- `npm audit --omit=dev --audit-level=low` завершает проверку ошибкой при любой известной уязвимости production-зависимостей.
- `npm audit --audit-level=moderate` проверяет полный граф, включая инструменты. Находки `low` видны в отчёте, `moderate`, `high` и `critical` завершают проверку ошибкой. Это явный порог, без подавления ошибок через `continue-on-error`.
- `task api:audit` запускает закреплённый govulncheck; его ненулевой код завершения останавливает задание.

Аудит зависит от доступности реестра npm и базы уязвимостей Go. Ошибка запроса не считается успешной проверкой. Нулевой результат означает отсутствие находок в рамках конкретного инструмента на момент запуска, а не доказанную безопасность всего приложения. Известные ограничения базового образа PWA описаны в [отчёте аудита каркаса](../openspec/changes/bootstrap-pwa/security-audit.md).

## Локальное воспроизведение

Из `apps/pwa`:

```sh
npm ci
npm run check
npm run build
npm audit --omit=dev --audit-level=low
npm audit --audit-level=moderate
```

Из корня, с установленными Go и Task; для `-race` нужен C-компилятор:

```sh
task api:fmt:check
task api:lint
task api:test:race
task api:build
task api:audit
docker build -f apps/pwa/Dockerfile -t posostavu-pwa:ci .
docker build --target api -t posostavu-api:ci apps/api
docker build --target migrate -t posostavu-migrate:ci apps/api
docker build --target runtime -t posostavu-postgres:ci infra/postgres
```

## Слияние и дальнейшее подключение

Перед слиянием проверяется успешный статус `CI status` для актуального коммита. Локальные и ручные проверки, не покрытые workflow, по-прежнему указываются в PR.

Конфигурация workflow не изменяет branch protection и существующие права доступа. После первого подтверждённого запуска итоговый статус `CI status` можно отдельно включить в обязательные проверки ruleset для `develop` и `main`; для веток `release/*` сначала нужно расширить события workflow. В текущей задаче правила GitHub не меняются.

CI не выпускает релиз, не запускает миграции на сервере и не выполняет деплой. Публикация образов, секреты окружения, запуск миграций, проверка после выкладки и откат относятся к следующему этапу CD.
