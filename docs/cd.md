# Доставка выпуска

Реализация [PRD-31](https://linear.app/po-sostavu/issue/PRD-31) подготовлена в репозитории. Публикация GHCR и выкладка выключены. Установка на VPS, выпуск сертификата и первый деплой выполняются отдельно после проверки PR.

## CI и CD

`ci.yml` проверяет приложения, собирает четыре образа и сохраняет `docker save` с gzip level 1. Каждый архив содержит метаданные SHA, image ID, размера и SHA-256. Интеграционный тест загружает эти же образы и запускает изолированный стенд. Из `develop` образы в GHCR не публикуются.

Артефакты PR и develop хранятся один день, успешного push main — семь дней. Имена содержат SHA и номер попытки CI. При повторе части заданий артефакты разных попыток не смешиваются: если четырёх образов текущей попытки нет, нужно повторить весь CI. Если срок хранения истёк, CD завершается ошибкой. Пересборки внутри CD нет.

Локальный замер 8 ноября 2026 года: PWA — 24,2 МиБ, API — 8,1 МиБ, мигратор — 7,7 МиБ, PostgreSQL — 113,7 МиБ. Всего 153,7 МиБ, экспорт отдельного образа занял от 0,37 до 3,96 секунды. Это размеры локальных сборок, не замер сети GitHub. Время передачи проверяется по шагам Upload и Download в CI.

В [CI с Go-инструментами](https://github.com/po-sostavu/app/actions/runs/42424274361) четыре артефакта заняли 177,4 МиБ. Экспорт вместе с первым запуском Go-инструмента занял 11–16 секунд, загрузка каждого артефакта — 2 секунды. Скачивание всех четырёх — 3 секунды, проверка и загрузка в Docker — ещё 10 секунд. Интеграционный стенд отработал за 64 секунды. Для текущих размеров передача через Artifacts подходит, замеры следует повторить при росте образов. Хранение ограничено сроками выше и доступной квотой организации, бесплатность публичных runners не заменяет проверку [лимитов хранилища](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

`cd.yml` принимает только успешный `workflow_run` CI для push в main того же репозитория. Checkout и скачивание используют SHA и run ID завершившегося CI. Публикация загружает образы без сборки, проверяет их происхождение и не перезаписывает тег коммита другим image ID. Манифест выпуска создаётся после публикации всех четырёх образов и содержит их digest.

Настройки репозитория:

| Variable | Значение для включения | Назначение |
| --- | --- | --- |
| `CD_PUBLISH_ENABLED` | `true` | Разрешить публикацию после CI main |
| `CD_DEPLOY_ENABLED` | `true` | Разрешить job с Environment production |

Без этих значений workflow не публикует и не разворачивает приложение. Файл должен попасть в default branch, чтобы GitHub начал обрабатывать `workflow_run`. Порядок выпуска остаётся `develop → release/* → main`.

Job deploy получает SSH-ключ только после одобрения Environment production. Перед подключением он проверяет публичную доступность всех digest и совпадение выпуска с текущим main. Весь CD сериализован без отмены выполняющегося деплоя. Сервер дополнительно использует файловую блокировку и отклоняет устаревший run ID.

## GHCR

Выбраны публичные пакеты:

- `ghcr.io/po-sostavu/app-pwa:<SHA>`
- `ghcr.io/po-sostavu/app-api:<SHA>`
- `ghcr.io/po-sostavu/app-migrate:<SHA>`
- `ghcr.io/po-sostavu/app-postgres:<SHA>`

Новый пакет GitHub первоначально создаёт приватным даже для публичного репозитория. После первой разрешённой публикации администратор переводит все четыре пакета в public. До этого включать деплой нельзя. VPS скачивает их анонимно по digest, PAT не нужен. [Правила Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).

Публикация использует встроенный GITHUB_TOKEN с `packages: write` только в соответствующем job. Серверные `.env`, SSH-ключи и секреты провайдеров не входят в контексты сборки. Runtime-секреты устанавливаются администратором отдельно.

## Установка на сервер

Инструменты находятся в `tools/delivery`: `cmd/release` передаёт и публикует образы, `cmd/deploy` обрабатывает запрос на VPS, `cmd/smoke` проверяет изолированный стенд. Модуль использует только стандартную библиотеку Go.

Эти команды предназначены для отдельной согласованной установки из проверенного checkout. Они не выполняются из workflow. Сначала собрать бинарник командой `task cd:build`, сверить существующие файлы и сохранить текущую заглушку деплоя. Команда собирает Linux amd64 независимо от ОС разработчика. На VPS передаётся готовый бинарник и конфигурация.

```sh
sudo install -d -o root -g root -m 0755 /opt/po-sostavu/deploy
sudo install -d -o root -g root -m 0700 /opt/po-sostavu/secrets
sudo install -o root -g root -m 0755 tools/delivery/bin/posostavu-deploy /usr/local/sbin/posostavu-deploy
sudo install -o root -g root -m 0644 infra/production/compose.*.yaml infra/production/Caddyfile /opt/po-sostavu/deploy/
sudo install -o root -g root -m 0644 infra/postgres/init.sh /opt/po-sostavu/deploy/init.sh
sudo install -o root -g root -m 0600 infra/production/config.example.json /opt/po-sostavu/deploy/config.json
```

На VPS требуются Docker и Compose 2.30+ с `env_file.format: raw`. На обследованном сервере Compose 2.39.2. Обработчик собирается с CGO_ENABLED=0, компилятор Go и интерпретаторы на VPS ему не нужны.

Сохранить существующие forced command и ограничение sudo только на `/usr/local/sbin/posostavu-deploy`. Ключ не получает интерактивную оболочку, forwarding, группу docker или право редактировать серверные файлы. Обработчик не принимает аргументы командной строки. Один JSON до 4096 байт передаётся через stdin и проверяется до операций Docker. Переменная `SSH_ORIGINAL_COMMAND` не интерпретируется.

`config.json` и все родительские каталоги должны принадлежать root и быть недоступны для записи другим пользователям. В конфигурации заполнить:

- `domain` — `posostavu.ivanzubkov.ru`
- `edge_network` — существующая сеть, к которой подключён Traefik
- `traefik_directory` — путь на хосте к каталогу file provider, смонтированному в Traefik целиком. Нужен доступ на чтение файлов и включённый watch
- `http_entrypoint`, `https_entrypoint`, `cert_resolver` — реальные имена из конфигурации Traefik, без предположений по имени домена
- `observe_seconds` — окно проверки после переключения, по умолчанию 120 секунд
- `reserve_memory_mib`, `reserve_disk_mib` — свободный запас сверх нового комплекта и резервной копии

Файл маршрута `posostavu.yml` принадлежит только этому приложению. Скрипт атомарно заменяет его и не редактирует Compose Appwrite, ACME-хранилище или остальные маршруты. Caddy не знает внешний домен, работает по HTTP:8080 и обращается к API своего цвета.

Установить секреты с владельцем root и правами 0600 по примерам `infra/production/*.env.example`. Пароли должны быть разными случайными значениями длиной не менее 24 символов. `DB_PASSWORD` в api.env совпадает с APP_DB_PASSWORD, в migrate.env — с MIGRATOR_DB_PASSWORD. Compose читает значения буквально, включая `$`, без интерполяции. Пароли не передаются в аргументах команд.

Рабочие файлы `.env`, config.json, архивы и состояние CD исключены из Git. Примеры содержат пустые значения и не подходят для запуска.

## Выкладка и откат

Общая PostgreSQL работает в проекте `posostavu-db`. Её volume, внутренняя сеть и образ живут независимо от двух цветов. При первой установке закрепляется digest PostgreSQL. Следующие выпуски приложения публикуют новый образ PostgreSQL, но не обновляют работающий сервер БД. Обслуживание и обновление БД выполняются отдельно.

У цветов `posostavu-blue` и `posostavu-green` отдельные сети приложения. Только Caddy подключается к внешней сети Traefik. API и PostgreSQL не публикуют порты хоста. Контейнеры ограничены по памяти, CPU, числу процессов и размеру логов. Суммарный предел памяти двух комплектов и БД — 1280 МиБ, мигратор может дополнительно занять 128 МиБ. Это лимиты, а не доказательство достаточного запаса на VPS.

Перед изменениями проверяются MemAvailable, свободный диск и наличие сети. Перед миграцией создаётся `pg_dump -Fc`, затем проверяется читаемость через `pg_restore --list`. Копии сохраняются в `/opt/po-sostavu/backups`, автоматически не удаляются. Перед включением CD нужны пробное восстановление в отдельную БД, копирование вне VPS и согласованный срок хранения. Только после этого администратор выставляет `recovery_verified: true` и `enabled: true`. Эти флаги подтверждают выполненную подготовку, сами её не выполняют.

Миграции запускаются отдельным контейнером только для нового выпуска. Ошибка блокирует переключение. Скрипт проверяет новый комплект через Caddy, меняет маршрут, проверяет публичный HTTPS и SHA из `/healthz`, наблюдает комплект и останавливает прежний. Уже начатым запросам остаётся окно наблюдения и до 30 секунд graceful shutdown.

При неудачной публичной проверке возвращается прежний файл маршрута. Автоматический возврат допустим только для выпуска с подтверждённой совместимостью. `infra/production/release-policy.json` проверяется перед публикацией. Значение `rollback_compatible: true` требует проверки старой PWA с новым API, новой PWA с прежним API и обеих версий API с расширенной схемой БД. Нельзя оставлять его true для несовместимых изменений.

Для ручного возврата к сохранённому предыдущему выпуску администратор передаёт тому же обработчику JSON. `expected_sha` защищает от отката уже изменившегося активного выпуска:

```json
{"operation":"rollback","expected_sha":"0123456789abcdef0123456789abcdef01234567"}
```

Откат не выполняет миграции down, не восстанавливает БД из копии и не удаляет файлы новых PWA. Хешированные assets и workbox-файлы сохраняются в общем `/opt/po-sostavu/assets`. Одинаковый путь с другим содержимым блокирует выпуск. Очистка истории — отдельная операция после прекращения поддержки соответствующих PWA.

`deploy/state.json` хранит активный и предыдущий выпуск, закреплённую БД и старший run ID. `deploy/in-progress.json` отмечает незавершённую операцию. При ошибке обработчик сохраняет причину в root-only `deploy/last-error.json`, если каталог прошёл проверку прав. Вывод Docker и значения окружения в него не копируются. После прерывания или ошибки миграции администратор проверяет фактический маршрут, контейнеры, состояние миграций и резервную копию. Удалять журнал для слепого повтора нельзя. Dirty-состояние и неизвестный результат миграции автоматически не исправляются.

## Проверки и границы

`task cd:check` проверяет gofmt, запускает закреплённый линтер проекта и тесты валидации, архивов, идемпотентности и отказов. `task cd:build` собирает обработчик для Linux, `task cd:audit` запускает существующий govulncheck. В CI также выполняются race detector и сборка. На Windows пропускается проверка Linux-блокировки файлов, на Linux CI выполняются все.

Задание `Delivery integration` использует четыре образа из CI, отдельные случайные имена проектов, синтетические пароли и собственный Traefik. Оно проверяет реальные миграции, два цвета, переключение, откат, сохранение данных и старой статики. После теста удаляются только созданные им ресурсы. Проверка использует HTTP на loopback и не подтверждает ACME или HTTPS рабочего VPS.

Каркас пока не содержит продуктовых API. Healthcheck подтверждает инфраструктуру, но не OCR, анализ состава или работу профиля. Эти сценарии нужно включать в проверку выпуска по мере реализации.

До первого деплоя остаются проверка контейнерных находок Caddy и gosu, ресурсного запаса сервера, внешних резервных копий, HTTPS и доступности GHCR. Старый PostgreSQL других проектов не относится к этому Compose. Его публичный доступ закрывается отдельно после проверки зависимых приложений.
