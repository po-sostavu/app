# API ПоСоставу

> REST API приложения для разбора состава и выбора шампуня.

Технический каркас на Go и Fiber v2. Есть проверка конфигурации, подключение PostgreSQL, служебные endpoints, управляемая остановка, отдельный инструмент миграций и локальные проверки. Продуктовые модули и подключение PWA будут реализованы следующими изменениями.

## Возможности

- HTTP-сервер с ограничениями времени, размера запроса и количества соединений
- Проверка параметров окружения до запуска HTTP
- PostgreSQL через sqlx и драйвер pgx, ограниченный пул соединений
- Раздельные проверки жизни процесса и готовности БД
- JSON-логи через `slog`, серверный request ID и безопасные ошибки
- Завершение по сигналу с ожиданием текущих запросов и отменой оставшихся операций
- Миграции отдельной командой и отдельной ролью PostgreSQL
- Локальные форматирование, линтинг, тестирование, сборка и проверка уязвимостей
- Docker-образы API и миграций с непривилегированным пользователем

Авторизация, профиль, каталог, анализ фото, OCR и ИИ пока не реализованы. Пустых продуктовых endpoints и таблиц в каркасе нет.

## Стек

- Backend: Go 1.27.3, Fiber v2
- Database: PostgreSQL, sqlx, pgx
- Migrations: golang-migrate
- Configuration: go-envconfig, godotenv для явно выбранного локального файла
- Logging: стандартный `log/slog`
- Architecture: Clean Architecture с элементами DDD, разделение commands и queries
- API contract: OpenAPI
- Code quality: gofmt, golangci-lint v2
- Tests: стандартный `testing`
- Security check: govulncheck

Версии зависимостей указаны в `go.mod` и `go.sum`. Инструменты разработки закреплены в `tools/go.mod` и `tools/go.sum` отдельно от зависимостей приложения.

## Архитектура и организация кода

Бэкенд — одно приложение с продуктовыми модулями. Точка входа вручную собирает зависимости. Домен не зависит от HTTP, PostgreSQL и внешних API.

Команды изменяют состояние через прикладной сценарий, доменные правила и транзакцию модуля, владеющего данными. Запросы чтения выполняют SQL и возвращают DTO без восстановления доменных объектов. Для чтения допустимы JOIN между таблицами модулей. Это не даёт права изменять чужие таблицы. Проверки доступа и входных данных обязательны для обеих сторон.

Разделение не требует отдельных БД, command/query bus, брокера или event sourcing. Структура будущего модуля и направление зависимостей описаны в [internal/README.md](internal/README.md).

| Путь                           | Назначение                                       |
| ------------------------------ | ------------------------------------------------ |
| `cmd/api`                      | Сборка зависимостей и запуск HTTP API            |
| `cmd/migrate`                  | Создание, применение и откат миграций            |
| `internal/platform/config`     | Чтение и проверка конфигурации                   |
| `internal/platform/postgres`   | Пул соединений PostgreSQL                        |
| `internal/platform/httpserver` | HTTP-настройки, health endpoints и формат ошибок |
| `internal/platform/lifecycle`  | Запуск listener и управляемое завершение         |
| `migrations`                   | Пары SQL-файлов. Продуктовых миграций пока нет   |
| `tools`                        | Зафиксированные Go-инструменты разработки        |
| `../../contracts/openapi.yaml` | Контракт реализованных HTTP-методов              |
| `../../infra`                  | Общий локальный запуск PWA, API и PostgreSQL     |

Сервер обрабатывает соединения конкурентно. Отдельная goroutine запускает listener. Канал передаёт результат его работы, а канал готовности и `sync.Once` согласуют запуск с возможным ранним сигналом остановки. Контексты задают срок выполнения запросов, проверки БД и завершения приложения. Во время штатной остановки текущим запросам даётся время завершиться. По истечении срока их контексты отменяются.

У Fiber v2/fasthttp отключение клиента само по себе не отменяет прикладной контекст. Ограничение ожидания обеспечивают явные deadlines и методы БД с `Context`. Будущие HTTP-адаптеры должны соблюдать тот же контракт. В каркасе нет очередей, фоновых продуктовых задач или распределённой синхронизации. Общие бизнес-инварианты нескольких экземпляров API в дальнейшем обеспечиваются PostgreSQL, а не локальным mutex.

## Endpoints

| Метод | URL       | Результат                                                                    |
| ----- | --------- | ---------------------------------------------------------------------------- |
| `GET` | `/livez`  | HTTP 200, если HTTP-процесс работает. БД не проверяется                      |
| `GET` | `/readyz` | HTTP 200 при успешной проверке PostgreSQL, HTTP 503 при ошибке или тайм-ауте |

Успешный ответ:

```json
{ "status": "ok" }
```

Ошибка готовности:

```json
{
  "error": {
    "code": "dependency_unavailable",
    "message": "Service is not ready",
    "request_id": "server-generated-id"
  }
}
```

Сервер создаёт `X-Request-ID` для каждого запроса. Значение из входящего заголовка не принимается как собственный идентификатор. Ответы содержат `Cache-Control: no-store`. Неизвестный маршрут возвращает HTTP 404 с кодом `not_found`. SQL, пароль подключения и внутренние ошибки зависимости в ответ не включаются.

Публичные служебные методы не дают доступа к пользовательским данным. Контракт хранится в [OpenAPI](../../contracts/openapi.yaml). Отдельного Swagger UI пока нет. При недоступной БД во время старта API завершается с ошибкой. Если БД пропала после запуска, `/readyz` возвращает 503, а `/livez` остаётся доступным.

## Переменные окружения

Примеры: [`.env.example`](.env.example) для API и [`.env.migrate.example`](.env.migrate.example) для миграций. Файл загружается только через `-env-file`. Автоматически искать `.env` приложение не будет. Уже заданные переменные процесса имеют приоритет, включая явно пустые значения.

### HTTP и логи

| Переменная              | По умолчанию     | Назначение                                              |
| ----------------------- | ---------------- | ------------------------------------------------------- |
| `HTTP_ADDR`             | `127.0.0.1:8081` | Адрес и порт listener                                   |
| `HTTP_REQUEST_TIMEOUT`  | `10s`            | Deadline прикладного контекста запроса                  |
| `HTTP_SHUTDOWN_TIMEOUT` | `10s`            | Срок ожидания запросов при остановке                    |
| `HTTP_READ_TIMEOUT`     | `5s`             | Ограничение чтения запроса                              |
| `HTTP_WRITE_TIMEOUT`    | `15s`            | Ограничение записи ответа. Больше request timeout       |
| `HTTP_IDLE_TIMEOUT`     | `30s`            | Ожидание следующего запроса keep-alive                  |
| `HTTP_BODY_LIMIT`       | `1048576`        | Максимальный размер тела в байтах. Для текущего каркаса |
| `HTTP_CONCURRENCY`      | `1024`           | Максимальное количество одновременных соединений Fiber  |
| `LOG_LEVEL`             | `INFO`           | Уровень slog: `DEBUG`, `INFO`, `WARN`, `ERROR`          |

Ограничения формата и размера фото будут определены при реализации анализа. Текущий лимит тела запроса их не задаёт.

### PostgreSQL

| Переменная             | По умолчанию    | Назначение                                          |
| ---------------------- | --------------- | --------------------------------------------------- |
| `DB_HOST`              | `127.0.0.1`     | Хост PostgreSQL                                     |
| `DB_PORT`              | `5432`          | Порт PostgreSQL                                     |
| `DB_NAME`              | `posostavu`     | Имя БД                                              |
| `DB_USER`              | `posostavu_app` | Рабочая роль. Для миграций `posostavu_migrator`     |
| `DB_PASSWORD`          | Обязательна     | Пароль выбранной роли                               |
| `DB_SSLMODE`           | `verify-full`   | Проверка TLS. `disable` только для локальной БД     |
| `DB_MAX_OPEN_CONNS`    | `10`            | Верхняя граница пула API                            |
| `DB_MAX_IDLE_CONNS`    | `5`             | Число свободных соединений, не больше максимального |
| `DB_CONN_MAX_LIFETIME` | `5m`            | Срок жизни соединения в пуле                        |
| `DB_CONNECT_TIMEOUT`   | `5s`            | Ограничение начального подключения                  |
| `DB_QUERY_TIMEOUT`     | `2s`            | Ограничение текущей проверки готовности             |

Порты, размеры пула и тайм-ауты проверяются при запуске. Пустой пароль и недопустимая конфигурация завершают процесс до открытия HTTP-порта. Ошибка содержит имя параметра без его значения. Внешняя PostgreSQL должна использовать `verify-full` и доверенный сертификат. Режимы с незаметным переходом на незашифрованное соединение не поддерживаются.

Пароли не передаются аргументами команд и не коммитятся. Изменение `.env` не меняет пароль уже созданной роли PostgreSQL.

## Локальный запуск

### Требования

- Go 1.27.3 в PATH
- Docker с Compose v2 для локальной PostgreSQL
- Task (Go Task) 3.54.0 для команд запуска и проверок в Ubuntu

Если Go установлен, но команда `go version` не найдена, проверить PATH и открыть новый терминал после установки.

Установить зафиксированную версию Task и добавить каталог Go-бинарников в PATH:

```sh
go install github.com/go-task/task/v3/cmd/task@v3.54.0
export PATH="$(go env GOPATH)/bin:$PATH"
task --version
```

При использовании собственного `GOBIN` в PATH должен находиться он. Для постоянной настройки добавить нужный каталог в конфигурацию своей оболочки.

### Установка

Все команды Go выполняются из `apps/api`:

```sh
go mod download
```

### Настройка окружения

Из корня репозитория:

```sh
cp infra/.env.example infra/.env
cp apps/api/.env.example apps/api/.env
cp apps/api/.env.migrate.example apps/api/.env.migrate
```

Заполнить пустые поля паролей в `infra/.env` разными локальными значениями. В API `.env` указать `DB_PASSWORD`, совпадающий с `APP_DB_PASSWORD`. В `.env.migrate` — пароль из `MIGRATOR_DB_PASSWORD`. Пустые пароли отклоняются проверкой конфигурации. При изменении `POSTGRES_PORT` согласовать `DB_PORT` в обоих файлах API.

### Настройка базы данных

Из корня репозитория:

```sh
docker compose --env-file infra/.env -f infra/compose.yaml up -d --build --wait postgres
```

Из `apps/api`:

```sh
go run ./cmd/migrate -env-file .env.migrate up
```

Каркас не создаёт продуктовых таблиц: каталог миграций пока пуст. Команда проверяет подключение и сообщает, что применять нечего. Служебную версию хранит golang-migrate.

### Запуск

Из `apps/api`:

```sh
go run ./cmd/api -env-file .env
```

API доступен на `http://127.0.0.1:8081`. Проверка:

```sh
curl --fail http://127.0.0.1:8081/readyz
```

Остановка — `Ctrl+C`. Для запуска собранного приложения использовать `go build -o bin/api ./cmd/api` и `./bin/api -env-file .env`.

## Миграции

SQL-файлы хранятся в `migrations`. Каждому изменению соответствует пара с последовательным шестизначным номером, например `000001_add_profiles.up.sql` и `000001_add_profiles.down.sql`. Это пример имени будущей миграции, а не существующая таблица.

Миграции выполняются **отдельно от запуска API** и под ролью `posostavu_migrator`. При старте второго экземпляра API схема повторно не меняется. Подключение передаётся через `DB_*`, а не через DSN в командной строке.

### Создание

Из `apps/api`:

```sh
go run ./cmd/migrate create add_profiles
```

Либо:

```sh
task migrate:create NAME=add_profiles
```

Имя — латинские строчные буквы, цифры и подчёркивания, начинается с буквы. Команда создаёт следующий номер и оба файла с `BEGIN` / `COMMIT`. Подключения к БД для создания файлов не требуется. Заполнить прямое изменение в `.up.sql` и обратное в `.down.sql` до применения. Уже применённую миграцию не переписывать — создавать следующую.

Параллельное создание в одном каталоге защищено файлом `.create.lock`. После аварийного завершения он может остаться: удалять его вручную только после проверки, что другой процесс `create` уже не работает.

Новая таблица по умолчанию принадлежит миграционной роли. В `.up.sql` явно выдать `posostavu_app` необходимые права на таблицу, а при использовании последовательности — `USAGE` на неё. Выбирать права по сценарию. Рабочей роли не нужны DDL, `TRUNCATE` и доступ к `schema_migrations`. Универсальной выдачи прав на все будущие таблицы нет.

Обычную миграцию выполнять в транзакции. Операции, которые PostgreSQL запрещает внутри транзакции, например `CREATE INDEX CONCURRENTLY`, оформлять отдельно с подходящим порядком восстановления при сбое. Шаблон `BEGIN` / `COMMIT` для них не подходит.

### Применение и проверка версии

```sh
go run ./cmd/migrate -env-file .env.migrate up
go run ./cmd/migrate -env-file .env.migrate version
```

`up` применяет все новые миграции. Повторный запуск без изменений успешен. `version` показывает номер и `dirty`. До первой миграции — `version: none; dirty: false`.

Флаги располагаются **перед командой**:

```sh
go run ./cmd/migrate -env-file .env.migrate -path migrations -timeout 60s up
```

`-path` по умолчанию равен `migrations`. Общий deadline команды — `30s`, допустимы значения от `1s` до `10m`. Прерывание или тайм-аут завершают команду с ошибкой. После этого проверить версию и фактическую схему перед повтором.

### Откат

Откатить один последний шаг:

```sh
go run ./cmd/migrate -env-file .env.migrate down
```

Полный откат — отдельное намеренное действие, которое может удалить данные:

```sh
go run ./cmd/migrate -env-file .env.migrate -confirm down-all
```

Перед откатом проверить `.down.sql`, совместимость работающего приложения и наличие нужной резервной копии. Откат кода сам по себе не откатывает БД. На тестовой БД проверять цикл `up → down → up` вместе с изменением схемы.

### Ошибка и dirty-состояние

Неуспешный SQL или прерывание могут оставить `dirty: true`. Инструмент не сбрасывает это состояние автоматически и не печатает полный SQL или ошибку драйвера с данными подключения.

1. Остановить повторные попытки миграции и проверить `version`
2. Сверить фактическую схему с `.up.sql` / `.down.sql`. Определить, какие действия уже выполнились, и восстановить согласованное состояние БД
3. После проверки вручную задать номер версии, которой **фактически соответствует схема**:

   ```sh
   go run ./cmd/migrate -env-file .env.migrate -confirm force 1
   ```

4. Проверить `version`, затем продолжить `up` при необходимости

`force 1` — пример, номер нельзя выбирать автоматически. `force` меняет только запись версии и снимает dirty-флаг: SQL не выполняется и схема не исправляется. Значение `-1` означает состояние до первой миграции и допустимо только после проверки, что схема действительно к нему возвращена.

### Запуск через Compose

Из корня репозитория:

```sh
docker compose --env-file infra/.env -f infra/compose.yaml run --rm --build migrate up
docker compose --env-file infra/.env -f infra/compose.yaml run --rm migrate version
docker compose --env-file infra/.env -f infra/compose.yaml run --rm migrate down
```

Каталог SQL в контейнере доступен только для чтения. `create` выполняется на компьютере. Полные команды настройки ролей и контейнеров — в [README инфраструктуры](../../infra/README.md).

## Сборка и запуск через Docker

Из корня репозитория после заполнения `infra/.env`:

```sh
docker compose --env-file infra/.env -f infra/compose.yaml up -d --build --wait postgres
docker compose --env-file infra/.env -f infra/compose.yaml run --rm --build migrate up
docker compose --env-file infra/.env -f infra/compose.yaml up -d --build --wait api
```

Эти команды запускают только API и PostgreSQL. API публикуется на `http://127.0.0.1:8081`. Порт меняется через `API_PORT` в `infra/.env`.

Общий запуск со статической PWA и шлюзом — `task up` из корня. Caddy на `http://127.0.0.1:8080` направляет `/api` и `/api/*` в Go с удалением префикса: `/api/readyz` соответствует внутреннему `/readyz`. `task check` проверяет шлюз, страницу PWA и готовность API с БД. Это техническая маршрутизация. Продуктовый API-клиент PWA и пользовательские методы пока не реализованы. Подробности — в [README инфраструктуры](../../infra/README.md).

Собрать образы отдельно:

```sh
docker build --target api -t posostavu-api:local apps/api
docker build --target migrate -t posostavu-migrate:local apps/api
```

Сборочный контекст — `apps/api`. В runtime остаются бинарник и доверенные CA-сертификаты. Go-инструментов и локальных env-файлов в образе нет. API и миграции запускаются с UID/GID `10001:10001`. Compose ограничивает права контейнеров и использует отдельные роли БД.

Compose настроен для локальной разработки. Общий Caddy использует `infra/Caddyfile`, отдаёт PWA и проксирует запросы в отдельный Go-сервис. Он работает по HTTP на loopback. Внешний HTTPS и CD настраиваются отдельно. Caddy не встраивается в Go-приложение.

```sh
go tool '-modfile=tools/go.mod' govulncheck ./...
```

Полная локальная проверка:

```sh
task check
```

`go test -race ./...` требует поддерживаемую ОС/архитектуру и C-компилятор для cgo. Race detector обнаруживает гонки памяти Go. Транзакционные гонки PostgreSQL проверяются отдельными интеграционными сценариями.

Тесты каркаса проверяют значимые ошибки конфигурации, HTTP-ответы и жизненный цикл. Доменные и интеграционные тесты бизнес-инвариантов появятся с соответствующими сценариями. В [CI](../../docs/ci.md) используются эти же команды: проверка формата, линтинг, тесты с `-race`, сборка и аудит. CD настраивается отдельно.
