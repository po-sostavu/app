# Правила Go API

- Установка зависимостей без согласования запрещена
- Перед изменениями читать корневой `AGENTS.md` и `docs/architecture.md`.
- Go-команды выполнять из `apps/api/`. Общие команды и OpenSpec — из корня репозитория.
- Стек: Go, Fiber v2, PostgreSQL, sqlx, golang-migrate, go-envconfig и стандартный `log/slog`. Зависимости — Go modules.
- Форматирование — стандартный `gofmt` из версии Go проекта. Альтернативный форматтер не подключать.
- Линтинг — golangci-lint v2 с конфигурацией `.golangci.yml`: `linters.default: none`, явно включены govet, staticcheck, errcheck, ineffassign и unused.
- Линтинг запускать из `apps/api/` командой `golangci-lint run ./...`. Локальный запуск и CI используют одну зафиксированную версию инструмента.
- В CI проверять формат без изменения файлов. Непустой вывод `gofmt -l` должен завершать проверку с ошибкой. Генерируемый и сторонний код исключать из форматирования и линтинга.
- Бэкенд — одно приложение с модулями `profile`, `analysis`, `catalog`, `tracking`. `platform` содержит техническую инфраструктуру.
- `cmd/api/main.go` использовать для сборки зависимостей и запуска приложения.
- Соблюдать Clean Architecture: домен не зависит от Fiber, sqlx, PostgreSQL и внешних сервисов.
- Прикладные сценарии координируют домен и задают границы транзакций команд. HTTP-обработчики отвечают за преобразование запросов и ответов.
- На стороне команд применять DDD и доменные бизнес-правила. Входные DTO допустимы, но не заменяют доменную модель изменения состояния.
- Запросы отделять от команд. Для чтения допустим SQL с возвратом DTO без восстановления доменных объектов.
- Проверять доступ и валидировать входные данные на обеих сторонах. Не выполнять изменения состояния в обработчиках запросов чтения.
- Разделение команд и запросов не требует отдельных БД, брокера сообщений или event sourcing.
- Реализации БД и внешних сервисов размещать на инфраструктурной стороне; интерфейсы определять на стороне потребителя.
- Не добавлять абстракции и пакеты без конкретного сценария. Каждый продуктовый модуль изменяет только свои таблицы. На стороне запросов разрешены SQL JOIN между таблицами модулей общей PostgreSQL с возвратом DTO; права на запись в чужие таблицы это не даёт.
- Межмодульные вызовы выполнять синхронно через прикладные контракты. Домен не импортирует домен другого модуля. Транзакция команды ограничена владеющим данными модулем; прикладная координация нескольких модулей не создаёт общую транзакцию.
- Использовать sqlx и обычный SQL. Squirrel в MVP не используется.
- Изменения PostgreSQL оформлять миграциями `.up.sql` и `.down.sql` в `migrations/`.
- Разделять общий разбор состава и персональную оценку. Не отправлять фото на сервер.
- Создавать и обновлять `contracts/openapi.yaml` вместе с HTTP-методами: запросы, ответы и ошибки должны соответствовать реализации.
- В MVP поддерживать OpenAPI-контракт вручную; автоматическая генерация клиентов и сервера не используется.
- Тестировать бизнес-правила и значимые прикладные сценарии стандартным пакетом `testing`: `*_test.go`, табличные тесты, команда `go test ./...`.
- Интеграционные тесты с реальной PostgreSQL добавлять для бизнес-инвариантов и транзакций, корректность которых зависит от БД. Использовать build tag `integration` и `go test -tags=integration ./...` с отдельной тестовой БД и миграциями проекта.
- Не писать тесты на каждый DTO, геттер, SQL-запрос, простую миграцию или техническую обёртку. Не повторять в тесте реализацию и не устанавливать целевой процент покрытия.
- Время и внешние сервисы контролировать через границы прикладных сценариев; не выполнять платные ИИ-вызовы в обычных тестах и CI. Проверки БД не должны обращаться к пользовательским данным.
- При исправлении ошибки бизнес-логики добавлять регрессионный тест. Для задачи без бизнес-логики новые тесты не обязательны; фиктивные тесты для каркаса не создавать.
- Не включать секреты в код, логи, примеры конфигурации и коммиты.
- Изменения постоянных архитектурных правил отражать в `docs/architecture.md` и этом файле. Решения отдельной задачи описывать в её `design.md`.

## Рекомендации агенту: конкурентность и надёжность

- Перед изменением конкурентного сценария определить общее состояние, владельца данных, бизнес-инвариант и последствия одновременных или повторных запросов. Различать гонки памяти Go и логические гонки в БД.
- Рассчитывать на несколько экземпляров API. Локальный mutex защищает только память своего процесса; целостность общих данных обеспечивать транзакциями, ограничениями и атомарными операциями PostgreSQL.
- Общие изменяемые данные Go защищать подходящей синхронизацией (`sync.Mutex`, `sync.RWMutex`, каналы или атомарные операции). Не добавлять goroutine без конкретной задачи; ограничивать их количество, обеспечивать отмену и завершение.
- Предотвращать тупики: захватывать несколько блокировок в согласованном порядке, сокращать критические секции и гарантировать освобождение блокировок при всех выходах. Не держать mutex или транзакцию БД во время внешнего HTTP/ИИ-вызова, ожидания пользователя или длительной обработки.
- Не полагаться на отдельные «проверить, затем записать» запросы. Для инварианта выбирать атомарный SQL, условное обновление с проверкой результата или блокировку строк в транзакции. Уникальность обеспечивать ограничением БД; `SELECT FOR UPDATE` не блокирует отсутствующую строку.
- Для повторной команды и операции с внешним эффектом продумывать идемпотентность между экземплярами. Внутрипроцессная дедупликация не гарантирует отсутствие дублей при масштабировании или перезапуске.
- При deadlock (`40P01`) или serialization failure (`40001`) откатывать транзакцию. Повторять целиком безопасную транзакцию с повторным чтением данных, ограниченными попытками и задержкой, учитывая общий deadline. Не повторять автоматически платные вызовы и другие внешние эффекты с неизвестным результатом.
- У запросов БД и внешних вызовов задавать конечные deadlines и обрабатывать отмену. Не допускать бесконечного ожидания блокировок, неограниченных повторов и накопления фоновых задач. При завершении процесса прекращать приём новых запросов и ограниченно ждать выполняющиеся операции.
- Ошибка внешнего API, тайм-аут или недоступность БД должны превращаться в контролируемую ошибку сценария и согласованный HTTP-ответ. Не использовать panic или завершение процесса для обычных ошибок зависимостей; исключить ложный успешный ответ.
- Отказ внешнего ИИ-сервиса не должен отключать независимые методы профиля и каталога. Ограничивать одновременные обращения к медленной зависимости, чтобы она не исчерпала ресурсы всего API. Повторы использовать только для временных ошибок и безопасных операций.
- Не хранить в памяти экземпляра единственное состояние, необходимое для корректности бизнес-операции. Считать кэш необязательным ускорением; ограничения на общие ресурсы и размер пула БД рассчитывать с учётом количества экземпляров. Миграции запускать один раз при развёртывании, не из каждого экземпляра API.
- Для затронутой конкурентной бизнес-логики запускать существующие тесты с `go test -race` в поддерживаемой среде. Значимые гонки БД, инварианты и откат проверять интеграционными тестами PostgreSQL; `-race` их не обнаруживает. Согласовывать запуск участников теста каналами или барьерами, а не случайными `sleep`.
- В диагностике сохранять request ID, код ошибки, зависимость и длительность операции. Клиенту не выдавать секреты, SQL, stack trace и необработанный ответ внешнего сервиса. Не заявлять устойчивость к отказам или отсутствие гонок без соответствующей проверки.

## Рекомендации агенту: ключи идемпотентности

- Для команд с побочными эффектами, которые клиент или инфраструктура могут повторить, использовать заголовок `Idempotency-Key`. Обязательность ключа, формат, срок хранения и ошибки фиксировать в OpenAPI соответствующей команды. Чистые запросы чтения ключа не требуют.
- Область уникальности ключа включает владельца запроса и операцию. Проверять права при каждом запросе: знание ключа не даёт доступа к чужому результату. Ключ не заменяет request ID, авторизацию или уникальные ограничения бизнес-данных.
- Хранить ключ, отпечаток значимых входных данных, состояние операции и завершённый результат в PostgreSQL. Атомарно закреплять ключ уникальным ограничением; не использовать схему «сначала проверить наличие, затем вставить» без защиты БД. Запись дедупликации относится к владеющему командой модулю.
- Тот же ключ с теми же данными возвращает сохранённый завершённый результат без повторного бизнес-эффекта. Тот же ключ с другими значимыми данными возвращает конфликт `409`, а не запускает новую операцию.
- Если операция с ключом уже выполняется, не запускать её повторно: возвращать документированный конфликт `409` с кодом состояния выполнения. Не обозначать незавершённую операцию успешной.
- Изменение бизнес-данных и фиксацию завершённого результата проводить в одной транзакции БД. Длительный внешний вызов выполнять вне транзакции: до него атомарно резервировать операцию, после него фиксировать подтверждённый исход. Не считать резервирование ключа гарантией однократного внешнего эффекта.
- Если внешний сервис поддерживает идемпотентность, связывать его ключ с нашей логической операцией и повторно использовать тот же ключ. После тайм-аута или падения с неизвестным исходом не запускать платный вызов повторно вслепую; сначала выяснять исход по контракту провайдера. Истечение блокировки или перезапуск экземпляра сами по себе не доказывают, что внешнего эффекта не было.
- Ограничивать размер ключей, срок хранения и доступ к сохранённым результатам. Защита действует в документированном окне хранения; клиент не переиспользует старый ключ для новой операции. При недоступности PostgreSQL не подменять защиту локальной памятью и не выполнять защищённую команду без неё.
- Проверять бизнес-сценарии повторного и одновременного запроса, несовпадения данных и восстановления после сбоя. При нескольких экземплярах они должны приводить к одному подтверждённому бизнес-результату, а не к дублям.

## Рекомендации агенту: безопасность бэкенда

- Ключи ИИ-провайдера, пароли PostgreSQL и ключи подписи получать только из серверной конфигурации окружения или хранилища секретов. Не возвращать их в API и не включать в исходники, образы, логи и примеры конфигурации. Не запускать приложение с демонстрационными секретами вместо обязательной конфигурации.
- Проверять подлинность запроса и разрешение на конкретное действие и объект, включая чтение и повторное получение результата по `Idempotency-Key`. Идентификатор пользователя из тела запроса не заменяет установленного сервером владельца; по умолчанию доступ закрыт.
- Валидировать структуру, типы, длины и диапазоны входных данных на сервере. Ограничивать размер тела запроса, время обработки и параллелизм; клиентская валидация не заменяет эти проверки.
- Все значения передавать в SQL параметрами. Динамические имена таблиц, столбцов и направления сортировки выбирать из разрешённого списка, а не подставлять из пользовательского или ИИ-текста.
- Не использовать CORS как авторизацию. Разрешённые origin задавать явно; не сочетать произвольный origin с credential-запросами. При cookie-аутентификации предусматривать защиту изменяющих состояние операций от CSRF и безопасные атрибуты cookies.
- Ответы ИИ и внешних API считать недоверенными данными: проверять структуру, ограничивать размер и не выполнять их как код, SQL или команды. Не выполнять серверные HTTP-запросы по произвольным пользовательским или сгенерированным адресам; допустимые назначения ограничивать, включая проверку перенаправлений.
- Использовать HTTPS и проверку сертификатов внешних сервисов; не отключать TLS-валидацию ради устранения ошибки. Рабочей роли PostgreSQL выдавать минимальные права, не использовать superuser; миграции выполнять отдельно с необходимыми для них правами.
- Не логировать Authorization, cookies, токены, пароли, полные запросы к ИИ, составы и профили. Безопасная диагностика содержит request ID, код ошибки, операцию и длительность; публичный ответ не содержит SQL, stack trace или сырой ответ провайдера.
- Ограничения злоупотребления и расхода внешнего API учитывать между всеми экземплярами приложения. Локальный rate limit одного процесса не считать общей квотой пользователя.
- Проверять значимые бизнес-правила доступа и изоляции данных: чужой профиль, чужой результат, повтор с чужим ключом. Не объявлять приложение безопасным по результату одного линтера и не добавлять формальные тесты на каждый технический элемент.
