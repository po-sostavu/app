# Design

## Context

В `apps/api` пока есть только правила. Реализованная PWA имеет отдельный контейнер. Подключения к API нет. Стек и продуктовые границы уже согласованы в `docs/architecture.md`. Пользователь поручил реализацию и небольшие коммиты. Дополнительное согласование того же объёма не требуется.

## Goals / Non-Goals

**Goals:** воспроизводимый запуск HTTP API и PostgreSQL, конечные ожидания, безопасные ошибки, отдельные миграции и проверяемые команды разработки.

**Non-Goals:** бизнес-модели и endpoints, идентификация пользователя, авторизация, OCR/ИИ, CI/CD, HTTPS и интеграция PWA. Не вводить учебные сущности для демонстрации DDD.

## Decisions

- `cmd/api` собирает зависимости вручную. `internal/platform` содержит конфигурацию, PostgreSQL, HTTP и жизненный цикл. Для продуктовых модулей принят шаблон `domain`, `application/command`, `application/query`, `infrastructure/postgres`, `transport/http`. Пакеты создаются вместе с первым реальным сценарием, без универсального Repository, шины и контейнера DI
- Команды используют домен и транзакции внутри владеющего данными модуля. Query-handler возвращает DTO через потребляемый им контракт чтения. SQL-адаптер выполняет `GetContext`/`SelectContext`, допустимы JOIN. Домен не восстанавливается ради чтения. Общая PostgreSQL остаётся источником согласованности. Модель чтения не получает право изменять данные
- Использовать установленную Go 1.27.3, Fiber v2, sqlx, pgx, go-envconfig, slog и golang-migrate. Версии фиксируются в Go modules и конфигурации инструментов. Конфигурация принимается через окружение. Локальный env-файл загружается только при явном указании, существующие переменные имеют приоритет
- HTTP listener работает в одной управляемой goroutine, ошибка приходит через буферизованный канал. `signal.NotifyContext` начинает shutdown. Контексты запросов имеют дедлайны. Во время нормального drain запросы завершаются, при истечении shutdown deadline отменяются. Контекст Fiber/fasthttp сам по себе не гарантирует отмену при отключении клиента, это ограничение документируется. Не создавать фоновые воркеры и mutex без общего изменяемого состояния
- `/livez` проверяет процесс, `/readyz` выполняет `PingContext`. Начальное подключение ограничено тайм-аутом, недоступная при старте БД приводит к ошибке запуска. Последующий отказ БД даёт 503 без остановки сервиса. SQL и сетевые ошибки в публичный ответ не попадают. Структурированные логи содержат безопасный код, request ID и длительность
- Миграции запускаются отдельным `cmd/migrate` и одноразовым сервисом Compose. DSN передаётся через окружение, не аргументы процесса. Команды: создание последовательной пары, up, down на один шаг, version. Аварийные down-all и force требуют явного указания и описаны отдельно. Пустой каталог допустим и не маскирует ошибки соединения. Первая продуктовая миграция появится с продуктовой таблицей
- `infra/compose.yaml` запускает только локальные API/PostgreSQL. Порты опубликованы на loopback, БД имеет именованный volume. Миграционная и runtime-роли разделены. Рабочая роль не superuser и не владеет схемой. Dockerfile собирает непривилегированные API и migrate targets. Caddy и PWA сюда пока не включаются
- Проверки: gofmt, golangci-lint v2, `go test`, `go test -race` в Linux, сборка и govulncheck. Тесты нужны для значимых ошибок конфигурации, ограничений ожидания и lifecycle, без искусственного покрытия пустого домена. Дымовые проверки PostgreSQL/миграций выполняются на отдельной тестовой БД
- Общие команды оформляются в `Taskfile.yml` для Go Task 3.54.0 и выполняются в Ubuntu/Linux. Локальный Taskfile API подключается в корне с префиксом `api:`. PowerShell-скрипты и Makefile не используются

## Risks / Trade-offs

- Конечный контекст требует участия SQL/HTTP-адаптера → все текущие операции БД используют Context-методы. Будущие адаптеры следуют тому же правилу
- Clean Architecture без продуктовых правил пока представлена соглашением о пакетах → не выдавать каркас за реализованные DDD-сценарии
- Compose предназначен для локальной разработки → TLS, шлюз, секреты окружения и CD настраиваются отдельной задачей
- Ошибка миграции может оставить dirty version → документировать диагностику и контролируемое восстановление. `force` не исправляет SQL и не выполняется автоматически

## Migration Plan

Создать локальные роли и базу, выполнить отдельную команду миграций, затем запустить API. Продуктовых таблиц пока нет. До использования реальных данных проверить up/down на отдельной БД. Применённые SQL-файлы впоследствии не переписывать. Откат приложения и откат схемы выполнять раздельно с проверкой совместимости.
