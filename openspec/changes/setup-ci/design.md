# Design

## Context

См. [proposal.md](proposal.md). PWA использует npm scripts, API — Go Task. Версии закреплены в `.nvmrc`, `package.json`, lock-файлах, `go.mod` и `tools/go.mod`. Проверки не требуют подключения PWA к API или рабочих OCR/ИИ-ключей. HTTP-контракт и продуктовые данные не меняются.

## Goals / Non-Goals

**Goals:** воспроизводимые Linux-проверки, независимые результаты PWA/API/контейнеров, один итоговый статус, ограниченное время и минимальные права.

**Non-Goals:** публикация артефактов, доступ к серверу, платные внешние вызовы, запуск продуктовых сценариев и изменение правил доступа GitHub.

## Decisions

1. Один `.github/workflows/ci.yml` на `ubuntu-24.04`: `pull_request` в `develop`/`main`, `push` в эти ветки, `workflow_dispatch`. Без фильтров путей, чтобы документационные PR тоже имели результат. Отдельные workflow и вычисление изменённых каталогов пока добавили бы лишние условия и риск пропущенной обязательной проверки
2. Задания `pwa`, `api`, `docker` независимы. Итоговый `ci` с именем `CI status` запускается через `always()` и принимает только `success` каждого предшествующего задания. У матрицы Docker `fail-fast: false`, чтобы были видны все три сборки
3. PWA: `npm ci`, `npm run check`, `npm run build`. Node читается из `.nvmrc`, npm — из `packageManager`. API использует закреплённый Task 3.54.0 и существующие задачи `fmt:check`, `lint`, `test:race`, `build`, `audit`. Обычный прогон тестов дополнительно не дублируется. Версия Go берётся из `apps/api/go.mod`, автоматическое переключение toolchain отключено. В runner доступен C-компилятор для `-race`
4. Кэшируются загрузки npm, модули и промежуточный build cache Go по lock-файлам. Go-ключ учитывает также `apps/api/tools/go.sum`. `node_modules`, env-файлы и готовые `bin`/`dist` артефакты в кэш не добавляются. Встроенных кэшей setup actions достаточно. Отдельный action кэширования не нужен
5. npm-аудит проверяет runtime с порогом low и полное дерево с порогом moderate. Это оставляет существующие low в инструментах видимыми без общего подавления аудита. Ошибки сети и более серьёзные находки завершают задание ошибкой. Go проверяется существующим govulncheck. Сборка контейнера не выдаётся за сканирование его ОС или Caddy
6. Docker использует штатный CLI runner, без дополнительных actions и реестра: PWA собирается из корня, API и migrate — из `apps/api`. Нет запуска PostgreSQL: текущим тестам он не требуется. Реальные интеграционные сценарии добавляются вместе с функциями
7. Actions закреплены полными commit SHA с комментарием версии. Workflow имеет только `contents: read`, checkout отключает сохранение credentials. Используется обычный `pull_request`, без `pull_request_target`, secrets, registry login или интерполяции пользовательских PR-текстов в shell
8. Тайм-ауты заданий и concurrency ограничивают расход ресурсов. Новый запуск для того же события/ref отменяет предыдущий. В документации описываются итоговый статус и способы локальной проверки. Branch protection автоматически не меняется

## Risks / Trade-offs

- Полная проверка каждого PR тратит больше минут → для текущих двух каркасов это проще и надёжнее фильтров. Есть кэши и отмена устаревших запусков
- Аудит зависит от сети и изменяемых баз уязвимостей → ошибка видна, повторный прогон допустим после восстановления сервиса. `continue-on-error` не используется
- Базы контейнеров PWA остаются существующими тегами → их закрепление и устранение известных ограничений базового образа рассматриваются отдельно. Этот CI подтверждает сборку
- Локальная проверка не доказывает выполнение на GitHub → в отчёте разделяются локальные результаты и первый реальный Actions run после публикации PR
- `workflow_dispatch` требует наличия workflow в default branch → первый удалённый запуск выполняется через PR. Основная ветка — `main`

## Migration Plan

Изменения не требуют миграции БД или конфигурации приложений. После публикации ветки первый PR в `develop` проверяет workflow на GitHub. Перед подключением `CI status` как обязательной проверки нужно подтвердить успешный и неуспешный удалённые прогоны. Действующие правила доступа сохраняются. Откат конфигурации выполняется обычным исправляющим PR. CD остаётся отдельной частью PRD-31.
